# hive-bridge

Where humans meet a hive: a chat bridge (Telegram first) and the Floor, a read-only live board. It's the human/agent half of One Hive release R7, shared by every hive; each hive brings only its configuration.

**Status (2026-11-09, v0.5.33):** runs live on 1-hive and on the proto-hive. Since v0.5.0 (2026-10-23: the Floor's bots view and the pinned status): decision cards answered by tapping, a grouped "Needs you", once-per-agent trouble alerts, the chief of staff at a usage limit, and new repositories by button (all below). Earlier (2026-10-19): extracted from [1-hive](https://github.com/1-hive/1-hive) with its history. Paths and ids are configuration (below); 1-hive runs it with the defaults. Group chats with several humans and bots work as in [`docs/design.md`](docs/design.md), when `telegram-groups.json` exists; without it, the bridge serves only the operator's private chat, as before.

- `telegram-bridge.py`: the operator's inbox and buttons, record pushes (approvals, escalations, unanswered questions, finished tasks, a daily digest), and chat with the chief of staff, who it wakes by fixed rules.
- `telegram-say.py`: send the operator one message from the host.
- `floor.py`, `floor/`, `floor_bots.py`: the Floor, a read-only board, in a browser or inside Telegram. Two views: **bots** (one card per agent: what it is doing now, what it owes, its last 24 hours; for hives of long-lived agents) and **goals** (one lane per goal, with replay at any record position).

**The design rule:** the bridge reports facts about each message (who sent it, what it replies to, its mentions) and never decides who it's for. One chief of staff, for the whole hive, interprets every human message and acts only through the record; workers never read the chat.

Related: [hive-record](https://github.com/1-hive/hive-record) (R1 + R2), [hive-runtime](https://github.com/1-hive/hive-runtime) (the operating loop), [hive-route](https://github.com/1-hive/hive-route) (R8).

## Taps only where they decide something

- **A goal you asked for starts on its own.** The bridge logs what operators write to the chief of staff
  (`.telegram/operator-words.jsonl`; hive-runtime's `op chat` adds the host session's). A proposed goal whose
  `hive-request` block quotes those words (3+ words, in order, from the last 14 days) and that asks for no host inputs is
  approved by the bridge; its card shows the words and **⏹ Stop**, which abandons it and tells the chief of staff to
  cancel its tasks. Anything else (the chief of staff's own idea, host files) gets the Approve card. `HIVE_AUTO_START=0`
  turns it off.
- **A completed goal with nothing to merge accepts itself** after `HIVE_AUTO_ACCEPT_DAYS` (3; 0 turns it off), with
  ↩ Reopen on its card and no reminders. With code to merge, ✅ Accept + merge as before.
- **🔀 Merge on a published pull request** (proto-hive's staged repositories): `telegram-say.py` gives the publisher's
  PR message a button when `HIVE_PR`/`HIVE_PR_SHA` are set and keeps the PR in `.telegram/prs.json`; any operator's tap
  runs `HIVE_PR_MERGE_CMD URL SHA` (proto-hive: `deploy/merge-pr`, i.e. hive-runtime's `publisher.py --merge-pr` as
  root), which merges with a merge commit only while the PR's head is still the reviewed commit.

Test: `tests/asking_is_approving_test.py`.

## Configuration

`hive_paths.py` reads the same environment variables as [hive-runtime](https://github.com/1-hive/hive-runtime), with the same defaults (1-hive's layout): `HIVE_ID`, `HIVE_GATEWAY_PORT`, `HIVE_URL`, `HIVE_CONFIG_DIR` (`telegram-token`, `telegram.json`, `telegram-bridge.key`, `floor.key`), `HIVE_WORK_DIR` (the bridge's state in `.telegram/`, the chief of staff's follow-ups and workspace in `cos/`) and `HIVE_WORKSPACE_REPO`. The chat with the chief of staff is the command in `TELEGRAM_CHAT_CMD` (hive-runtime's `cos.sh chat`).

## Group chats

Optional `HIVE_CONFIG_DIR/telegram-groups.json`. Without it, nothing changes for a private-chat hive.

```json
{
  "chats":  [{"name": "work", "chat_id": -1001234567890, "mode": "all"},
             {"name": "protobots", "chat_id": -5437945421, "mode": "mention"}],
  "humans": [{"name": "ben", "user_id": 111, "permissions": ["operator"]},
             {"name": "andy", "user_id": 222, "permissions": ["operator"]}],
  "bots":   [{"name": "protomega2", "user_id": 333, "username": "Protomega2bot", "actor": "worker.protomegabot2"}]
}
```

- **Two modes per chat.** In a `mode: all` chat (the work group) every allowed human's message goes to the chief of staff, the hive's only interpreter of what humans write. In a `mode: mention` chat (a conversation group) only messages that @-mention the bridge's bot or reply to it do, from humans and from the listed bots (a bot may ask the chief of staff for work); everything else there is context only.
- **Bots propose tasks through the record.** A bot that is asked for real work in any chat (private ones included) proposes it with its hive tool; the record holds the proposal, the bridge wakes the chief of staff for it, and once approved, the task's progress and result are threaded on the chat message the proposal cited.
- **The result comes back where the work was asked.** When a task started from a chat message closes, two replies go on that message: the report's `## Summary` section as text to read in the chat (a report without one gives its first ~800 characters), then the full report as a file to download, naming the code it changed (repository, commit, the task's branch).
- **Work never reaches a bot through chat.** Telling a bot it has a task is a control signal, not conversation (One Hive's channel discipline: "runtime is not speech"), so the bridge doesn't do it: the bot's sidecar delivers it through the bot's own runtime (hive-runtime: the Iter channel, or an OpenClaw gateway's webhook). A Telegram @-mention wake was tried in v0.4.1 and removed in v0.4.2.
- **A dialogue log.** Every message the bridge sees in a listed chat, humans' and bots', goes to `HIVE_WORK_DIR/.telegram/dialogue.jsonl` (chat, sender, text, reply), outside the task record, for search and for the record's message events later (R7). The message is sent as an envelope of facts: who wrote it, what it replies to and who wrote that, its mentions, the recent thread, and the hive's agents and tasks from the record. The chief of staff's reply is threaded on the message.
- **Bots' messages are thread context only,** never requests. Unknown senders and unlisted groups are ignored. `/board` works in a group.
- **One chief of staff, one queue across every chat.** A reply whose first line is `[[to: <chat name>]]` goes to that group, for example a result announced after a review passes.
- **The chief of staff's replies say which model wrote them.** `cos.sh chat` (hive-runtime v0.5.70) starts a reply with `[[model: <model>]]` when Claude Code's output names the model that answered; the bridge takes that line off and the reply goes out as `[claude-opus-5-5]` over the text (provider prefix and date suffix dropped, first piece of a long reply only). A worker's question and its result carry the same tag when the record event names the model that wrote it (hive-record A7, `data.ext.model`, filled in by `hive emit` 1.5.1). Unknown: no tag, never a guess. `HIVE_SHOW_MODEL=0` turns it off. Test: `python3 tests/model_tag_test.py`.
- **A task started from a message is threaded there.** When the chief of staff creates one, its reply carries `[[task: <id>]]`. The bridge then posts the task's progress (started, a question, result posted, review verdicts, done) as replies to that message.
- **Buttons** (approve, accept and the rest) stay in the operator chat (`telegram.json`), for any human with the `operator` permission.
- **Shadow evidence:** `HIVE_WORK_DIR/.telegram/addressee-rule.jsonl` logs what a mention-or-reply rule would have picked for each message. The rule never acts.
- **Telegram setup:** add the bot to the group, and turn its privacy mode off (BotFather: `/setprivacy` → Disable). Otherwise Telegram shows it only commands and replies to its own messages.

## The Floor's bots view

Three sources, never mixed up, and every line from a fixed rule (`floor_bots.py`; no model, and no agent writes its own status):
- **Now**, from **beacons**: each agent's sidecar or runner (hive-runtime v0.5.0, config `"beacon"`) posts every 30 s what the agent's own files say: the chat request it is answering (chat and message ids only), its queue, its route-hook episodes, its last step, an OpenClaw session's chat, a reviewer's current review or last failure. `POST /api/beacon`, signed with the agent's record key under the prefix `hive-beacon1` (never a valid record write). Never authoritative. No beacon for 150 s: offline. **Problems reach the operators:** when an agent's beacons report a problem for 10 minutes on end (`floor.py --alert-after`; e.g. a reviewer whose review command keeps failing, as when its model account is out of credits), the Floor messages the operators' chat once, with the error, saying the Floor shows it until it's fixed. There is no recovery message, and nothing when the agent flaps back: that agent is reported again only after a day without a problem (remembered across restarts in `state/alerted.json`). An agent whose beacon says its model account hit a usage, spend or credit limit can't run, a worker as much as a reviewer. Test: `python3 tests/problem_alert_test.py`. **And the chief of staff:** the bridge (with `FLOOR_BOARD=bots`) reads the Floor's `/api/status` `trouble` list each minute and tells the chief of staff once when an agent has been offline or unable to run for 10 minutes, with the Floor's detail (no recovery ping, none for a flap within a day), asking it to fix what it can rather than post about it; the record can't show either. Test: `python3 tests/trouble_ping_test.py`.
- **On its plate**, from the record: tasks assigned, in progress, blocked, in review, passed but not merged (the reviewed commit isn't on its branch in the hive's bare clone, floor.json `clones_dir`: the default branch if that holds the result's base, else the first other branch that does, as the publisher picks its pull request's, e.g. iter's `protomega`).
- **Needs you**, grouped: ❓ **Decide** (worker questions, operator escalations, chief-of-staff requests that are decisions) first, open; then ❗ **Fix** (agents that can't run, e.g. "<name> can't work" with the error and how many tasks it holds), 🔀 **Merge** (with the PR number), and the chief of staff's hive-fix requests folded into one line. Each says what to do in numbered steps: a passed result to merge (title: whose change, which repository, into which branch; a link that opens its pull request on GitHub, from the registry's GitHub fetch URL, onto the branch holding it, hive/<task> or -r2...), a chief of staff's request (its own title and first lines, the whole file folded under it; closed by telling the chief of staff in the Work group), a question or escalation (answered in the Work group).
- **Who asked what**, from the bridge's dialogue log: a request's or a task's chat message (a task's `cause.external`, `telegram:<chat>/<message>`) gives the person, the chat and the first line. Direct messages: never their content.

`floor.json` (in `HIVE_CONFIG_DIR`, or `FLOOR_CONFIG`): `view` (`bots` | `goals`), `names`, `initials`, `about`, `machines` ({machine: [actors]}), `chat_names`, `clones_dir`, `auth` (`telegram`, the default through a proxy, or `none`). `FLOOR_STATE_DIR` holds its beacon samples (default `HIVE_WORK_DIR/.floor`).

**Decision cards.** A worker's question file, or a chief-of-staff request with front matter `kind: decision`, can start with a card (`card.py`): a status line, "Before <action>:", and numbered questions each answerable in a word (`word: … / word: …`). The Floor shows the card under Decide; in the chat the question is its own reply, "❓ <task> needs a decision", with the question file attached, and one button per answer (`decision_buttons.py`). An operator's tap goes to the chief of staff, which records the answer. Tests: `python3 tests/decision_buttons_test.py`, `python3 tests/floor_cards_test.py`.

**Questions already decided aren't asked (v0.5.47).** On a chat-started task, a worker's question waits 10 minutes (`HIVE_QUESTION_GRACE_MINUTES`; 0 posts at once). If the chief of staff answers it by then, the reply under the task's status message says so: "✅ <worker> asked on <task>; the chief of staff decided it", the card, its answer (from the answer file's `Answer:` line on), "The work goes on with that", the same buttons, and the answer file. A tap there is a second opinion: the chief of staff is told the worker already went on with its answer, and puts the work right if the operator chose otherwise. Unanswered after 10 minutes: the ❓ question as before. On the proto-hive the chief of staff answers most within two minutes (36 of 40 worker questions, 2026-11-04 to 18), and each still reached the humans as a question.

**A long digest goes in parts (v0.5.53).** A digest over Telegram's 4096 characters is sent as several messages, split between lines, each after the first marked "part k of n". Only a failed first part means the digest wasn't sent and is tried again in 10 minutes; a later part that fails is logged, so the parts already out are never sent again. On the proto-hive (2026-11-25 08:00 to 11-26) the digest was too long, and Telegram refused it every 10 minutes for 31 hours. Test: `tests/goal_runs_on_test.py`.

**A conflict with main is said at once (v0.5.52).** A reviewed pull request that conflicts with main can't be merged by a tap or by trying again: on the proto-hive (2026-11-24) the standing order tried PR 45 for 20 minutes before saying so, its 🔀 stayed, and an operator's tap was refused with GitHub's bare "merge conflicts". Now the first refusal for a conflict, by the standing order or by a tap, says in reply to the PR's message that it conflicts with main and the chief of staff is having it redone on top of main, clears its 🔀 buttons, and asks the chief of staff, once per reviewed commit, to have it rebased and published again with a Supersedes line. The new PR merges by itself under a standing order, or gets its own 🔀. A PR given up on for a conflict before this version loses its buttons on the next step, quietly. A tap on a PR that was closed (superseded) clears its buttons too. Test: `python3 tests/auto_merge_test.py`.

**Merging on a standing order (v0.5.51).** `HIVE_AUTO_MERGE_REPOS` (`owner/name`, comma-separated, or `*`) names the GitHub homes whose reviewed pull requests the bridge merges itself once the publisher posts them, oldest first, as if `HIVE_AUTO_MERGE_BY` had tapped 🔀 Merge. It runs the same `HIVE_PR_MERGE_CMD`, so a PR merges only while its head is still the reviewed commit. On the proto-hive, every PR left waiting made the later ones conflict and need a rebase (2026-11-23). A merge is said in reply to the PR's message, its buttons are cleared on every copy, and the chief of staff is told. One found merged already, or closed because a later PR superseded it, just loses its buttons. A refusal is tried again every 10 minutes, 3 times, unless it can't change (closed, merged, head moved). Then the chat and the chief of staff are told once, so a conflicting PR is rebased and published again, and the new one merges. Only PRs from the last 14 days, at most 4 merge runs a step. A tap still works and says it's merged already. Off unless set. Test: `python3 tests/auto_merge_test.py`.

**The digest can't stop the bridge (v0.5.50).** v0.5.47's digest read a task's `status_since` as a time; the record keeps a position there, so the first digest after a goal's task was done raised, and the loop, which ran the digest first, raised again every 10 seconds: on the proto-hive, from 2026-11-20 08:00 UTC for 38 hours the bridge read no messages, sent no cards and woke the chief of staff for nothing (an operator fixed the deployed copy by hand on 2026-11-21; this is that fix). Each step of the loop (digest, inbox, feed, threads, status, floor alerts, the chief of staff's pings, idle goals) now runs on its own: an error is logged with its file and line and the other steps go on; a digest that fails is tried again in 10 minutes. The idle-goal wake counts a goal idle when none of its tasks is being worked on: a task created but never assigned doesn't keep it quiet any more, and the ping names such tasks; the digest's ⏸ line reads "nothing worked on since". Test: `python3 tests/goal_runs_on_test.py`.

**Cards in a group, and standing goals (v0.5.49).** `HIVE_CARDS_CHAT` (a chat id) sends the inbox cards (a goal to approve, ⏹ Stop, a completed goal to accept or merge, +budget, restart, a question waiting), their follow-ups and the digest to a group, e.g. the proto-hive's Work group, so every operator there sees and decides them. Taps count from operators only (telegram-groups.json `permissions`), in that group or the private chat. The card is edited in place in its own chat and names who tapped. Reopen/Abandon ask for the reason in the same chat, and only an operator's reply counts. `/merge`, `/inbox` and `/digest` from an operator there are handled by the bridge, not the chief of staff. Card state (`decided`, `pending_reason`, `inputs_shown`, `merge_shown`) is keyed by chat and message; older keys (the private chat's bare message ids) still work. A question already on its task's thread in that group isn't carded again. Unset: the private chat, as before. **Standing goals** (ids `standing-*`: one per line of work, approved once, never completed, holding a hive's small requests) get no "start it" ping on approval and no idle wake, and their over-budget card offers ⏱ +30 days. The Floor's goals view shows open tasks with no goal in a lane of their own. Test: `python3 tests/cards_chat_test.py`.

**A goal runs on without asking (v0.5.47; hive-runtime v0.5.71, docs/chief-of-staff.md "Running a goal").** When an active goal has had no open task for 30 minutes (`HIVE_IDLE_GOAL_MINUTES`; 0 turns it off), the bridge wakes the chief of staff once for that idle spell, to start the goal's next work or complete it; not a goal escalated to the operator (over budget). The daily digest shows, for each active goal, the tasks done since the last digest, the goal log's new lines (`goals/<date>-<goal>-log.md` on the workspace's main, one dated line per decision; each line shown once, counted when the digest is sent) and "⏸ no open task since …". Test: `python3 tests/goal_runs_on_test.py`.

**A goal's host inputs on its approval card.** A goal whose document declares host inputs (hive-runtime `inputs.py`: a `hive-inputs` block of host files its tasks may read) lists them on the 🆕 card under "Approving lets its agents read these host files". Approving grants them, so a tap on Approve only approves what that card showed: if the chief of staff revised the inputs since, the goal isn't approved, the old card loses its buttons and the current card goes out (`state.json` `inputs_shown`, per card). A block that can't be read is flagged on the card. Test: `python3 tests/goal_inputs_card_test.py`.

**Accept + merge.** A completed goal's 🏁 card says what its reviewed code would put into `main` (hive-runtime `merge.py`'s plan: fast-forwards and merge commits per repository, what's included, a mirror to merge upstream, a conflict). When there's something to merge, the buttons are ✅ **Accept + merge** (merges exactly the plan the card showed, then emits `goal.accepted` with the outcome as its note, and tells the chief of staff), ✅ **Accept only** (its status says `/merge <goal>` merges later) and ↩ Reopen. If the plan changed since the card (main moved, another result passed review), nothing is merged or accepted and the current card goes out (`state.json` `merge_shown`, per card). If merging fails, nothing is accepted and the card keeps its buttons. `/merge <goal>` sends a 🔀 Merge card for a goal accepted already; `/merge` alone lists recent goals whose reviewed code isn't in main. `HIVE_MERGE_PY` names merge.py (default: hive-runtime's, installed beside the bridge; empty turns merging off). Test: `python3 tests/goal_merge_card_test.py`.

**The chief of staff at a usage limit.** When its Claude account prints a usage, spend or credit limit, the operators get one alert with the line, messages to it are held (`state/cos-limit.json`, kept across restarts) instead of answered with the limit line, the oldest is retried every 20 minutes, and once one is answered the operators hear it's back and the rest are answered in order. Test: `python3 tests/cos_limit_test.py`.

**Tagging people.** The chief of staff's envelope lists `people` (each human in telegram-groups.json with a username: name, `@handle`, operator), so a plain `@username` in its reply notifies them.

**New repositories by button** (`HIVE_NEW_REPO_CMD`, e.g. `sudo -n /opt/hive/proto-hive/deploy/new-repo`; off when unset). When the chief of staff files a hive request whose front matter is `kind: new-repository` with `name`, `description`, `asked_by` and `cause: telegram:<chat>/<message>`, the bridge posts it as a reply to that message (else in the operator chat) with **Create** and **Decline**. Any human with the `operator` permission may tap, in that chat; others are refused, and a message is decided once. Create runs the command with the name and description (hive-runtime's `new-repo.py` behind it: the repository on GitHub, the publisher's key, a staged registry entry), records `hive.registry_changed` with the digest it prints, citing the asking message (this bridge's operator key: the SPEC lets only an operator record it), and tells the chief of staff. Agents never hold the GitHub credential; a human decides each repository. Test: `python3 tests/new_repo_buttons_test.py`.

**Other operators' private chats.** Any human with the `operator` permission in telegram-groups.json (not only telegram.json's user) can write to the bot privately: `/start` or `/help` explains, `/floor` and `/board` open the Floor, and anything else goes to the chief of staff, saying who wrote it, with its reply back in that chat. Approval buttons, the inbox and the digest stay in telegram.json's chat.

**Access.** From loopback without a proxy header: open (the bridge, an SSH tunnel). Through an HTTPS proxy (it sets X-Forwarded-For): only the hive's operators, by Telegram Mini App data signed with the bot's token (the Floor needs only the derived key, `telegram-webapp.key`), or by a 30-day cookie from a 15-minute login link the bridge gives an operator in a private chat (`/floor`; shared secret `floor-session.secret`). Run the Floor as its own user, without the bridge's keys.

**In Telegram** (bridge, with `FLOOR_BOARD=bots`, `FLOOR_URL`, `FLOOR_PUBLIC_URL`): a chat with `"status": true` in `telegram-groups.json` gets one status message, pinned once and edited in place when it changes (no notifications); `/board` answers with the same text; `/floor` (or `/start floor`) in an operator's private chat opens the Floor inside Telegram and gives a login link for a browser; the bot's menu button opens it too. `FLOOR_TG_APP` (a BotFather Mini App, `bot/app`) makes the group's button open it in one tap. The chief of staff's turns are logged for the Floor (`.telegram/cos-turns.jsonl`, `cos-now.json`).
